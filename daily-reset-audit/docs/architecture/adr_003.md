# ADR 003: Use IndexedDB with Dexie for Local Persistence

## Status

Accepted.

## Context

The initial Daily Reset prototype used `localStorage`.

As the product scope became more structured, the application introduced multiple related entities:

- CheckIn,
- CompletedAction.

The application also needed to support:

- persistent history,
- relationships between check-ins and completed actions,
- statistics,
- local data management,
- future extension of the local data model.

`localStorage` became too limited for this purpose.

## Decision

Use IndexedDB as the browser persistence mechanism.

Use Dexie.js as a wrapper around IndexedDB.

The persistence layer is implemented in:

- `lib/db.ts`,
- `lib/storage.ts`.

## Data model

### CheckIn

Fields:

- id,
- createdAt,
- energy,
- mood,
- mentalLoad,
- availableTime,
- classifiedState.

### CompletedAction

Fields:

- id,
- checkInId,
- activity,
- category,
- completedAt.

`CompletedAction.checkInId` links the completed action to the check-in that generated it.

## Consequences

Advantages:

- structured browser persistence,
- support for multiple entities,
- easier querying,
- clearer data relationships,
- better maintainability than localStorage,
- no backend required for the current MVP.

Trade-offs:

- slightly higher implementation complexity,
- asynchronous data access,
- browser-local storage remains device-specific.

## Privacy

All current application data remains in the user's browser.

The current MVP does not transmit check-in data to a remote server.

## Relation to previous decisions

This ADR supersedes:

`ADR 001: Use localStorage for Prototype Persistence`

ADR 001 is retained as part of the architectural decision history.

## Rationale

IndexedDB with Dexie provides enough structure for the current MVP without introducing unnecessary backend infrastructure.

This keeps the architecture aligned with the project's local-first and narrow-scope strategy.
